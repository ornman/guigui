# 意外恢复系统设计（Resilience Design）

> 状态：**已确认（Approved）** — 架构与所有开放问题均已定，下一步转实施计划。
> 日期：2026-06-15
> 关联：`docs/PRD.md`（PRD 规划了 tray.py / poller.py，但实际从未实现）

---

## 1. 背景与问题

### 1.1 触发事件

2026-06-15（今天）`login.log` **一条记录都没有**，意味着 06:55 的 `--silent` 任务今天根本没执行。

### 1.2 根因：三套机制只有一套是自主的

| 机制 | 现状 | 问题 |
|---|---|---|
| 定时任务（06:55 每天 `--silent`） | ✅ 唯一真正自主登录的入口 | **单点故障**，今天没触发（关机/睡眠未唤醒/任务被破坏） |
| 开机自启（`auto_start: true`） | 开机后确实启动 | 但启动的是 GUI，而 `App.__init__` **既不自动登录也不自动开轮询**——窗口开起来干等着 |
| 断网重连（轮询） | 配置 `polling_enabled: false` | 关着的；即使开着，也只在手动点「应用设置」后才生效 |

**结论：只要 06:55 那次被错过、且用户没手动操作 app，这一整天都不会登录。** 这就是今天的情况。

### 1.3 PRD 的欠债

`docs/PRD.md` 原本规划了 `tray.py`（系统托盘）+ `poller.py`（独立轮询）+ 三种运行模式（交互/静默/托盘），明确"单进程"原则。但实际代码只实现了 GUI 和 `--silent`，**托盘与"关窗最小化到托盘继续轮询"从未实现**（代码里 grep 不到任何 pystray/tray 代码）。本设计顺便补齐这笔欠债。

## 2. 设计目标（已与用户确认）

- **架构**：混合（Windows 任务计划做保底 + 托盘常驻守护进程做秒级重连）
- **覆盖场景（全选）**：
  1. 开机/重启/唤醒后自动登录
  2. 白天掉线（认证超时/WiFi 掉线/服务器重启）快速重连
  3. 进程自身崩溃后自动重启
  4. 任务计划/自启项被破坏后自修复
- **原则**：坚持 PRD 的"单进程"——一个 exe 三个 CLI 模式。

---

## 3. 架构总览（五层）

| 层 | 职责 | 状态 |
|---|---|---|
| **L1 自主启动** | app 一启动就 `attempt_login` 一次 + 自动开轮询 | 🆕 需补（现在 `App.__init__` 两样都没做） |
| **L2 托盘常驻** | 补齐 `tray.py`：轮询开启时关窗 → 最小化到托盘，后台持续轮询 | 🆕 需补（PRD 欠债） |
| **L3 多触发器任务** | 任务计划从"每天一次"升级为"登录时 + 每 15min 心跳 + 每天 06:55"，每次都幂等 | 🔧 改造 |
| **L4 看门狗** | 心跳 `--ensure` 发现托盘没活就拉起（方案 A：心跳即看门狗） | 🆕 需补 |
| **L5 自修复** | 心跳/启动时把"任务/自启/配置"按 config 意图对齐，被删就重建 | 🆕 需补 |

## 4. 进程模型与入口

| 入口 | 行为 | 谁调用 |
|---|---|---|
| `exe`（无参数） | GUI 模式：开窗 → 自动登录一次 → 自动开轮询 → 关窗最小化到托盘。启动时做一次自愈对齐 | 用户双击 / 开机自启注册表 |
| `exe --silent` | 一次性登录 + 通知结果（**保留**，向后兼容 / 手动用） | — |
| `exe --ensure` | 🆕 **心跳**：幂等登录 + 看门狗 + 自修复，**默认静默**（仅当真发生恢复/失败才弹通知） | 任务计划的所有触发器 |

**单实例锁**：Win32 命名互斥量（`Local\SchoolAutoLogin-Instance`，会话级），不用文件锁——进程崩溃时 OS 自动释放，不留死锁。GUI/tray 模式抢占它；已存在实例就把现有窗口提到前台再退出。`--ensure` 不抢 GUI 互斥量（它是临时检查），但拉起托盘时托盘进程会抢。

## 5. 触发器与场景映射

### 5.1 任务计划触发器（L3）

从"每天一次"升级为三个触发器，都跑 `--ensure`：

1. **登录时**（`-AtLogon`）— 覆盖开机/重启后的会话登录
2. **每 15min 重复**（心跳）— 看门狗 + 自修复的载体
3. **每天 06:55**（保留 `scheduled_login_time`）— 兜底的早晨登录

设置沿用 `-StartWhenAvailable -WakeToRun -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries`。

### 5.2 场景覆盖表（含审查修正）

> ⚠️ **审查修正**：初稿误以为「登录触发器」能覆盖"睡眠唤醒"——这是错的。`-AtLogon` 只在会话登录时触发，**唤醒不产生登录事件**。修正见下表"唤醒"行。

| 场景 | 主力 | 兜底 |
|---|---|---|
| ① 开机/重启/登录 | 登录触发器 + 自启注册表 → app → 自动登录 | — |
| ① **睡眠/休眠唤醒** | **托盘轮询（~30s）**——进程在睡眠时被挂起而非被杀，唤醒后轮询自动恢复 | 心跳(15min) |
| ② 白天掉线 | 托盘轮询(30s) → wifi 修复 + 重连 | 心跳(15min) → `--ensure` 登录 |
| ③ 进程崩溃 | 心跳(15min) → `--ensure` 发现托盘没活 → 拉起 | — |
| ④ 任务/自启被删 | 另一侧存活入口 → 自愈重建 | 同时被删则不可恢复（合理边界） |

---

## 6. 核心 insight：自愈是"互为兜底"

场景 ④ 有个绕不开的硬限制：**如果任务计划本身被删了，没有任何东西会跑 `--ensure`，它没法把自己重建。** 所以自愈必须靠"另一个独立入口"互为兜底：

```
开机自启(注册表) ──启动──▶ app 进程 ──启动自愈──▶ 重建【任务计划】
        ▲                                              │
        └────重建【自启注册表】◀──自愈──── 任务计划心跳(--ensure) ──┘
```

- **app 进程**（被自启/双击/心跳拉起）启动时 → 按 config 意图重建【任务计划】和【自启注册表】
- **任务计划 `--ensure`** → 按 config 意图重建【自启注册表】、拉起 app 进程

两者互为兜底：任意一个还活着，就能把另一个重建。只有"自启和任务计划**同时**被删"才无法自愈——这等价于"用户彻底卸载"，是合理边界（无法与"手动卸载"区分）。

---

## 7. `--ensure` 的职责（原子三件事）

每次心跳触发，`--ensure` 顺序做：

1. **幂等登录**：`attempt_login(cfg)`。已登录则秒返（`check_auth_status` → "logged_in" 直接返回，不发凭据），所以每 15min 一次的服务器压力可忽略。
2. **看门狗**：尝试抢占 GUI 互斥量；能抢到 = 托盘没活 → detached 拉起托盘进程；抢不到 = 已在跑，跳过。
3. **自修复**：按 config 意图对齐自启注册表（缺失且应为开 → 重建；应为关却存在 → 不动，尊重用户手动操作）。

> 注：app 进程启动时还会额外对齐【任务计划】（互为兜底的上半边）。

## 8. 配置变更（草案）

| 字段 | 默认 | 含义 |
|---|---|---|
| `resilience_enabled` 🆕 | `true` | L3/L4/L5 总开关。关掉则退回旧行为（仅每日定时 + 手动） |
| `heartbeat_interval_minutes` 🆕 | `15` | 心跳频率（任务计划重复间隔） |
| `polling_enabled` | `true`（默认改为开） | 是否对断网主动重连；托盘常驻本身由 `resilience_enabled` 决定 |
| `polling_interval_seconds` | `30` | 托盘轮询间隔（不变） |
| `scheduled_login_enabled` / `scheduled_login_time` | `true` / `06:55` | 早晨兜底触发器（语义不变） |
| `auto_start` | `true` | 自启注册表（语义不变） |

## 9. 审查发现与开放问题

### 已修正（无需再问）
- **唤醒映射**：见 5.2，已改为"托盘轮询为主、心跳兜底"。
- **`--ensure` import 路径**：必须像 `--silent` 一样**只 import `src.config/login/notify`**，绝不拖入 customtkinter，否则心跳冷启动又慢又重。已确认 `main.py` 现有 `run_silent` 就是这个轻量路径，`--ensure` 复用。
- **通知刷屏**：托盘 `_poll_worker`（`src/app.py:476`）每次重连都发通知，网络抖动会刷屏。**修正：只在状态转换时通知 + 限流（如每 N 分钟最多一条）。**

### 已定决策（用户已确认）

**问题 2 — 心跳不做 WiFi 切换。** `--ensure` 心跳仅"可达就登录，不可达就放弃"，不 `netsh` 切 WiFi。WiFi 修复只留给托盘轮询和早晨 06:55 登录，避免在非校园网下每 15min 扰民。需为 `--ensure` 提供一个"仅登录、不做 WiFi 修复"的入口（或给 `attempt_login` 加 `skip_wifi` 参数）。

**问题 3 — 托盘常驻与 polling 解耦，polling 默认改 true。** 新增 `resilience_enabled`（默认 true）决定托盘是否常驻；`polling_enabled`（默认改为 true）只管"是否对断网主动重连 + 重连频率"。托盘本身（健康检查 + 看门狗载体）在 `resilience_enabled` 下始终在跑。

**问题 5 — 仅异常时重建 + 一次性迁移。** 自愈只在"任务缺失 / 触发器规格与新版不符 / enabled 状态与 config 不符"时才重建，平时不动，不覆盖用户手动改动。另做一次性迁移：新版首次运行把旧单触发器任务重写为多触发器规格。

**问题 7 — 保留 06:55。** 作为用户可配置的显式"早晨登录"（`scheduled_login_enabled=false` 可关），日志里留一条确定的早晨记录。

## 10. 测试策略

### 单元（pytest + mock，不依赖网络/系统）
- `--ensure` 的三个子决策函数（该不该登录 / 该不该拉起托盘 / 该不该重建自启），各自返回"动作列表"再执行——决策逻辑可纯函数化测试。
- 自愈谓词：模拟"任务缺失/状态不符"的输入，断言只在该重建时重建。
- 互斥量封装：acquire/release 行为（mock win32）。
- 配置校验：新字段 `resilience_enabled` / `heartbeat_interval_minutes` 的合并与回退。

### 手动（无法自动化）
- 实际创建任务计划 → 关机 → 开机 → 验证登录。
- kill 托盘进程 → 等 ≤15min → 验证心跳拉起。
- 删任务计划（保留自启）→ 验证下次 app 启动重建。
- 睡眠/唤醒 → 验证托盘轮询在 ~30s 内重连。

## 11. 非功能

- 打包：`main.spec` 需加入 pystray/Pillow 数据文件 + 托盘 .ico。
