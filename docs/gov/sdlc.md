# 单人 + AI 协作 SDLC

> 治理文档之一。本项目是**一个人 + 若干 AI agent** 开发:人是唯一拍板者与验收者,agent 负责探查、起草、执行、复核。本文定义「一个想法」到「已固化变更」经过的六个阶段:每阶段**谁做、产出什么、过门条件、本仓库真实例子**。配套:提示词模板(`prompt-templates.md`)、文档法(`document-management.md`)。

## 0. 全流程一页图

```
S1 需求 ──► S2 拍板 ──► S3 计划 ──► S4 执行 ──► S5 验收 ──► S6 固化
(人开口)   (人选,agent呈报)  (agent起草,人过目) (agent干)   (agent自证+人抽查) (commit+记忆+同步)
   ▲                                                                                    │
   └────────────────── 新需求 / 验收不过打回 / 回顾发现的债 ◄──────────────────────────┘
```

铁律横贯全程:**拍板项永远停给人,纯执行项 agent 自动接力;每阶段有门禁,不过门不进下一阶段。**

## S1 需求 —— 把话说清楚

- **谁**:用户口述;agent 复述理解、编号提问(大型需求走多轮问答制:复述 → 编号提问 → 拍板 → 再问,不许猜)。
- **产物**:小需求 = issue 段落或计划文档一节;大需求 = PRD 修订(docs/prd/,产品语义正本)。
- **门禁**:agent 能用自己的话复述出「用户会看到什么」且用户点头;文案/交互类需求必须落到具体画面,不接受抽象动词。
- **实例**:「自助服务平台链接」事故(2026-09-06)——用户指的是动态渲染的拒绝文案里的链接,agent 在静态 HTML 搜不到就自作主张加到设置页,被打回。教训固化为「定位链」纪律(见 T2 模板)。

## S2 拍板 —— 决策只出自人

- **谁**:用户。agent 的职责是**收拢选项、给事实、不代拍**。
- **产物**:产品决策 → PRD 修订;技术取舍 → ADR(docs/adr/,快照不改写);文案 → 场景化拟稿清单过目。
- **门禁**:呈报必须大白话 + 用户画面(「国庆在家桂桂…」),禁术语、禁默认值、禁替用户列选择题;已拍板项沉淀进 SPEC §4 决策基线。
- **呈报纪律**:收尾前先二筛——能写出清晰启动话术的是纯执行项,直接干;写真拍板才呈报。**不要**呈报完再跟一句「下一步可以 1/2/3」把选择权甩回用户。
- **实例**:ADR-0005 签名——agent 列了五条路径的事实表(成本/收益/前提),状态「待拍板」,三个月后翻出来仍能续上上下文;这就是拍板文档化的价值。

## S3 计划 —— 写成零上下文可执行的作战文档

- **谁**:agent 起草,用户过目(讲方案≠许可,点头才动)。
- **产物**:docs/plans/<主题>-YYYY-MM-DD.md(快照),必含四件:**病灶(实测证据)→ 修法(函数落点)→ AC(验收标准)→ 执行约定**(测试基准/契约规则/不顺手修/拍板项分离)。
- **门禁**:计划自带「执行约定」节,让新会话或 subagent 零上下文能跑;交付两件套(路径 + 启动话术,AGENTS.md 已固化);交互类计划必须有交互规范层(病灶→规范→落点→AC),纯架构骨架会被打回。
- **实例**:ui-interaction-rework v2 —— 8P0+9P1+3P2 逐项带 AC,收尾批 subagent 靠同一句启动话术接力到全部闭环。

## S4 执行 —— 主会话还是 subagent?

- **判据**:能写出清晰启动话术 → spawn subagent;写不出 → 说明还是拍板题或探查题,回 S1/S2。**多 agent 并行 = git worktree 物理分支,完成 squash 回 master**,不许串行在 master 叠无关 commit。
- **纪律**(进 subagent 提示词,详见 T3 模板):只干范围内的事、不顺手修、只 add 自己的文件、测试基准从仓库根跑、真机/真实数据操作先声明边界(如「绝不碰在岗任务」)。
- **门禁**:代码进 master 前,该单元的测试在位且全绿;mock 注缝必须用对(GGMock.login 而非直赋,GG.api 是 Proxy)。
- **实例**:杀软整改批(2026-09-11)——一个 subagent 按 ADR 实施清单连落 4 个 ADR、6 个 commit、322 测全绿,期间为守「不碰真实任务」纪律主动跳过一条清单项并如实报告。

## S5 验收 —— 自证 + 抽查,两层都要

- **谁**:执行 agent 自证;主会话(或另一个 agent)抽查;用户做产品级确认(看真实画面)。
- **门禁**(按 SPEC §3 质量基线):pytest 322 底线只增不减;触达前端场景跑动态验收 runner;触达用户承诺的,**审计每个承诺的验证链**(不只验逻辑对——「通知会发吗、发了用户看得见吗、被拦了会怎样」);真机项如实标注(环境跳过不算通过)。
- **实例**:动态验收 runner 的诞生(2026-09-11 前夜)——静态走查说「全绿」,数据化复测立刻抓出 mock 老用户 `pwd=null` 自洽 bug。mock ≠ 真机,mock 绿只是入场券。

## S6 固化 —— 不固化的活等于白干

- **谁**:agent,机械执行。
- **清单**:① git commit(每单元,信息说清做了什么为什么);② 状态收口(计划标已闭环/ADR 标已接受/索引同步);③ 矩阵/契约同步义务触发即做;④ 记忆沉淀(**只记方法论、环境事实、教训**——代码结构 git 里有,不重复);⑤ 新坑入 ops.md 坑表。
- **实例**:本仓库的记忆条目「runner 方法学/视图类名/.v-boot 延时阈值」都是验收方法沉淀;而「scheduler.py 有哪些函数」从不入记忆——git 永远比记忆准。

## 门禁自动化缺口(已知,挂 roadmap P2)

当前所有门禁是**人工/agent 自律**,无 pre-commit/CI 拦截:pytest 不会自动跑、commit 信息无模板校验、拍板项混进执行无法机检。这是 2026-09-10 已确认的缺口,修法见 roadmap;在自动化到位前,以 SDLC 各阶段门禁为准。
